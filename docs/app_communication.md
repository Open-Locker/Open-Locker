# App Communication Guide

Client applications communicate with the Laravel backend through REST and
Laravel Reverb. The mobile app never connects directly to MQTT.

## Backend interfaces

The REST contract is generated by Scramble and is available through the OpenAPI
documentation. Relevant endpoints include:

- `GET /api/compartments/accessible` returns the authenticated user's
  compartments grouped by locker bank.
- `POST /api/compartments/{compartment}/open` starts an open command and returns
  `202` (`pending`) or `403` (`denied`) with a `command_id`.
- `GET /api/compartments/open-requests/{commandId}` returns the persisted command
  state. It is available to clients as a polling fallback.
- `PUT /api/compartments/{compartment}/content-note` updates or clears the
  compartment's content note.

The presence of an endpoint does not mean the current mobile app consumes it.
See [Current mobile behavior](#current-mobile-behavior).

## Reverb channel

Compartment broadcasts use:

- private channel: `users.{userId}.compartment-status`;
- authorization endpoint: `POST /broadcasting/auth`;
- Laravel Echo with the Reverb broadcaster.

Channel authorization is defined in `locker-backend/routes/channels.php`.

### Available events

**Open command progress** — `.compartment.open.status.updated`

```json
{
  "command_id": "uuid",
  "compartment_id": "uuid",
  "status": "accepted|denied|sent|acknowledged|opened|already_open|door_jammed|failed",
  "error_code": "nullable-string",
  "message": "nullable-string",
  "compartment_number": "nullable-integer",
  "locker_name": "nullable-string"
}
```

`compartment_number` and `locker_name` are nullable human-readable context. For
denied requests, clients localize known stable reason codes in `message` and use
a generic fallback for unknown values. See ADR-0045.

**Door state** — `.compartment.door_state.updated`

```json
{
  "compartment_id": "uuid",
  "door_state": "open|closed|unknown",
  "door_state_changed_at": "nullable-ISO8601-string"
}
```

**Content note** — `.compartment.content_note.updated`

```json
{
  "compartment_id": "uuid",
  "content_note": "nullable-string",
  "content_note_updated_at": "ISO8601-string",
  "content_note_updated_by_user_id": 123
}
```

## Current mobile behavior

The React Native app currently:

1. fetches the accessible-compartments list through REST;
2. subscribes to the private Reverb channel;
3. applies door-state and content-note events directly to the cached
   accessible-compartments result;
4. invalidates that cache when the socket becomes unavailable or disconnected,
   and when the app returns to the foreground, causing a REST refetch;
5. sends the open mutation and reports only whether that initial request was
   accepted or failed.

The mobile open mutation does **not** retain the returned `command_id`, consume
`.compartment.open.status.updated`, or poll the open-request endpoint. Open-status
events and polling are backend capabilities available to clients, not an
implemented mobile fallback.

## Open-state semantics

Intermediate states are `accepted`, `sent`, and `acknowledged`. An
`acknowledged` command means the unlock pulse was sent; it does not prove that
the door opened.

Terminal states are `opened`, `already_open`, `door_jammed`, `failed`, and
`denied`. Since ADR-0040, `opened` means that the physical door was observed
open. Clients must not treat `acknowledged` as equivalent to `opened`.
